How it works

What gets committed, and how often.

Lune commits three kinds of thing. Records: any JSON object an adapter serves, put into a canonical form first, so the same record always produces the same fingerprint. Readings: sensor telemetry, appended in groups as it arrives. Structure: each unit's record names its parent, so which units make up an assembly is committed along with the units themselves.

On a schedule, the daemon closes a checkpoint. A checkpoint binds the structural tree and the telemetry range together under one root, and each checkpoint is anchored in one transaction. When the demo runs on the live deployment on Arbitrum Sepolia, it closes a checkpoint every 30 seconds; on a local chain it closes one every 10.

The chain

What the chain holds.

For each checkpoint, the chain holds one root: a fingerprint of everything the checkpoint committed. Beside the roots it holds the hash of the key that signs the checkpoint manifests. Both live in a small registry contract that your organisation deploys with its own key.

No data, no record and no reading goes on chain. A reader of the chain learns that something was committed, not what. The registry accepts one root per checkpoint id and refuses a second, so a root that has been anchored cannot be replaced.

The live registry on Arbitrum Sepolia: 0xD2Fa28a9c959Da2709740Ba12802A88b7E9F7403.

The check

What a verifier checks.

The badge shows six checks for the record, in these words. Each one has to pass for the verdict to read ATTESTED.

  1. 1 Record matches its committed fingerprint. The verifier puts the record it was shown into canonical form, hashes it, and compares the result with the fingerprint that was committed.
  2. 2 Fingerprint is in the committed structure. It follows the path from that fingerprint up to the root of the structural tree the checkpoint names.
  3. 3 Readings are in the committed telemetry range. Each reading shown is hashed and traced to the root of the telemetry range the checkpoint covers.
  4. 4 Checkpoint recomputed. From the checkpoint's fields, including the two roots, it recomputes the checkpoint's own root.
  5. 5 Checkpoint manifest signed by the registered key. It checks the manifest's ML-DSA signature against the key whose hash your organisation registered in the contract.
  6. 6 Checkpoint root is anchored on chain. It reads the root stored on chain for that checkpoint and compares it with the one it recomputed.

When readings are present, a seventh row, Shown readings match the attested readings, compares the readings shown with the attested ones.

There are three verifiers, in Go, JavaScript and Python, and they agree on a shared set of test vectors. None of them needs Lune's servers to be trusted: each works from the data shown, its proof and the chain. The proof format is a written specification, verifier/SPEC.md, so a third party can implement a verifier of its own.

Assemblies

How one check covers an assembly.

Each assembly's record carries a fingerprint of its members: every member's identifier and the fingerprint of that member's own record. A member that is itself an assembly carries its own, so the top fingerprint depends on every part beneath it.

Nothing else changes. It is one more attested field, so the six checks above are what verify it, and one signature check and two chain reads cover an assembly of any size.

In the viewer, the fingerprint is rebuilt from the live scene, not taken from the server. A verdict of ATTESTED therefore says the machine in front of you is the machine that was committed.

When the check fails, the viewer names the part only after confirming that the records it was given are themselves bound to the chain. If they are not, it says the assembly does not match and that it cannot say where. It never guesses.

Where it plugs in

Lune sits beside the twin, and the check runs in the viewer.

Adapters. An adapter tells Lune how to read a source's REST API and its MCP tools: which objects to commit, and which fields of each. Two exist, for the Nextspace knowledge twin and for an OpenUSD warehouse scene with a maintenance API, and both run on recorded fixtures of those APIs. An adapter can be written for any source that serves its objects over REST.

The proxy. Lune's proxy stands in front of the twin's own REST and MCP APIs. It passes each response through and adds two members beside each object: an attestation, the proof a verifier needs, and an attestation_reason, the proxy's short account of it, such as anchored, not yet anchored or altered. The verdict is the verifier's, not the proxy's: a proof that is missing or fails to check reads NOT VERIFIED.

The viewer badge. In Omniverse Kit, the badge is an extension: a Provenance section in the Property panel with the six checks, a label in the viewport over the selected object, which shows the selected object's verified readings from the past minute under the verdict, and a box around the object in the verdict's colour. For an assembly the panel adds one line for the whole assembly, or one line for each part that changed. In a browser, it is two web components; the daemon's own demo page uses them to show the same verdicts. Both rest on the verifiers above, so any viewer that can run one of them can host the badge.

The chain. Development runs on a local Anvil chain, and the live deployment is on Arbitrum Sepolia. The chain is a matter of configuration, and Lune can anchor on any EVM chain.

What can be attested

The full list, in the terms of your own systems.

Asset identity and class Asset registers and PLM The identifier and class shown are the ones committed. A reclassified asset reads NOT VERIFIED and names the field.
Parent and assembly membership Asset registers and PLM, and the 3D scene's hierarchy The asset sits under the parent committed for it. A part given a different parent reads NOT VERIFIED, and from its assembly it is reported as moved, with both parents named.

Limits

What it does not do.

  • It attests records and readings, not derived answers. A query that computes an average returns a number Lune never committed. The readings it averaged are attested; the average is not.
  • It does not make a wrong record right. If a source system recorded the wrong value, Lune commits that value faithfully. What it adds is that a value changed after it was committed becomes visible.
  • There is nothing on the chain to hide: it holds roots and a key hash, never a record or a reading. The records and readings stay in your systems.
  • A whole-assembly check covers what assemblies hold. A record committed beneath a part, with no assembly above it, is covered by no assembly's fingerprint.
  • It does not replace access control, backups or the twin itself. Who may see a record, how it is kept safe and where it is shown stay as they are. Lune checks what is shown.
Status

Where it stands.

As of 2026-11-20, Lune's demo anchors to Arbitrum Sepolia, a public test network (chain id 421614), in the registry at the address above, deployed at block 326446150; when it runs, it closes a checkpoint every 30 seconds. The demo scene holds 269 units, and a whole assembly checks in one step: a conveyor of 12 parts, or the scene's 268.
